# SM-04 — SQLite and Project Library

## Objective

Port the v1 Library/project/task/diagnostic/scenario stores to system SQLite3
with the exact filenames, schema, pragmas, snapshots, project isolation,
one-time legacy migration and deletion safety. A copied v1 Library must survive
read/write/close/reopen without semantic drift.

## Implementation boundary

- Keep `library.sqlite`, `project.sqlite`, and legacy `slatesync.sqlite`; retain
  WAL, foreign keys, a 5-second busy timeout, private `0700` directories and
  `0600` database/JSON files.
- Keep the exact v1 tables, indexes, `scenario_observations.profile_id` foreign
  key and `ON DELETE SET NULL` behavior. Do not introduce a schema version 2 or
  an ORM/dependency.
- Keep the Library database as a project-folder index. Each project owns its
  own database, project metadata/settings, tasks, diagnostics and scenarios.
  The native project runtime exposes task create/update/list/load/delete,
  diagnostic create/list/load/delete, and scenario import/read/observation
  operations through the same project lease boundary.
- Keep task and diagnostic JSON payloads forward-compatible by preserving
  unknown keys. SQLite remains authoritative; atomic JSON snapshots remain
  import/export compatibility artifacts, and one malformed snapshot cannot
  prevent other rows from loading.
- Keep `.slatesync-project` and `.slatesync-library` transfer behavior at v1:
  reject links, boundary escapes, future/malformed manifests and existing
  destinations; stage ordinary files, use SQLite online backup for every
  database, validate before atomic publication, and omit WAL/SHM/tmp artifacts.
- A project import receives a new project identity and rebinds project/library
  ownership in `project_meta`, task/diagnostic JSON and valid snapshots while
  preserving malformed legacy snapshots as opaque evidence. Activating or
  relocating a Library persists its path and closes all outgoing connections
  before returning a restart-required result to the native app composition root.
  On the next launch that composition root must lazily read `settings.json`,
  reopen an arbitrary selected Library unchanged, and migrate only known
  historical default locations; a configured legacy default remains
  authoritative when the preferred path is already occupied.
- Migrate the legacy global database/snapshot directories once into
  `project-default` using `legacy_migration_v1`; inject missing project
  ownership without deleting or modifying the legacy source.
- Retain default-project archive/delete protection. Destructive deletion must
  reject new leases, wait for active operations, close every project database,
  rename to a unique tombstone, compensate the rename if index deletion fails,
  and retry safe tombstone cleanup on later bootstrap.
- Treat actor reentrancy as part of the persistence contract: Library/startup
  and project-store bootstrap use one shared in-flight task; project terminal
  operations retain exclusive ownership until completion; runtime shutdown and
  Library activation are single-flight. A Library rename drains snapshot writes
  before moving its directory, and every outgoing owner is offered close even
  when another close reports an error.
- Concurrent imports of one Scenario Profile resolve to one canonical row.
  Transfer-tree enumeration errors fail closed, and a failed SQLite backup is
  closed before its main/WAL/SHM artifacts are removed.
- Persist normalized Scenario Profiles and observations in SM-04. Scenario
  learning/similarity remains SM-05 behavior and must not be reimplemented here.
- Keep all automated tests on explicit temporary roots. The user's default
  Application Support and Project Library remain out of scope.

## Verification and governance

The implementation is ready for formal review when SwiftPM build/tests, Xcode
Debug/Test Plan, the SM-04 contract audit, Node/Modern compatibility baselines,
static/type/build checks, native ABI lifecycle, Gate self-tests and
`git diff --check` pass. `./script/phase_gate.sh SM-04 --allow-dirty` is
diagnostic only. Formal completion still requires a dedicated clean review
commit, clean Gate evidence, a phase review report and explicit Repository
Owner approval before `CURRENT_STATE.json` advances.

The Gate result classifier treats a macOS UI runner failure to initialize or a
timeout enabling automation mode as `BLOCKED_ENV`, even when xcresult reports a
failed-test count. Assertion, uncaught-exception and application-crash evidence
always takes precedence and remains `FAIL`.

## Tracked findings from earlier phases

- `SQLiteDatabase.rows` must distinguish terminal `SQLITE_DONE` from
  `SQLITE_BUSY`, `SQLITE_ERROR`, and other step failures instead of returning a
  partial result. The implementation maps busy/locked errors to retryable
  `SQLITE_BUSY`, other row-step failures to stable `SQLITE_ROWS`, and includes a
  malformed JSON virtual-table regression that fails during `sqlite3_step`.
