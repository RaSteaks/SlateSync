## 准入、成功定义与不可变边界

### 准入检查

开始 WP-0 前必须同时满足：

1. SM-08 已按 `PHASE_GATES.md` 走完 `REVIEW_READY → PASS → COMPLETE`，状态文件与 review
   指向同一已批准 commit；dirty diagnostic 或旧阶段 PASS 不能替代。
2. 原生 App 已覆盖 Project Library、Workspace、Recognition、CSV、Settings、Logs、Help，
   所有 SM-08 acceptance/performance/resource tests 可从干净 checkout 执行。
3. Electron/React/Node 兼容源与测试仍完整存在，足以运行最后一次 pre-cutover matrix。
4. 工作树干净、release/cutover Owner 单独授权，删除清单和保留清单已审阅。

任何一项不满足，SM-09 保持 `NOT_STARTED`；不得用“先删后补测试”的方式制造不可验证状态。

### 成功定义

SM-09 的完成由两个连续、不可互相替代的证据点组成：

1. **Pre-cutover compatibility commit**：在旧 Node/Electron oracle 仍存在、且 WP-2～WP-5
   对 Xcode/resources/package/CI/release 的修改已经纳入后，完整 Swift + Electron/Modern/Node
   差分矩阵再次通过，冻结 source/output/evidence manifest；SM-08 approved commit 上的首次
   baseline 不能替代这个删除前最终证据点。
2. **Final native cutover commit**：其 parent/ancestry 可验证地包含上述 compatibility commit；
   Electron/React/Node production inputs 已删除，最终 Gate 只依赖 Swift/Xcode/macOS 系统工具，
   原生 Run/Debug/Test/Archive、bundle/package/data/signing audits 全部通过。

最终 Gate 不假装重新执行已经被合法删除的 Node 测试，而是校验 pre-cutover evidence 的精确
commit、hash、PASS 状态和 ancestry，并运行所有迁移后的原生 acceptance tests。旧测试不能在
没有等价覆盖/冻结证据时删除，也不能为了让 final Gate 变绿而静默降低断言。

### 不可变边界

1. 最终产品仅支持 macOS 15.0+，一个 Universal app 同时包含 arm64 与 x86_64；不得把两个
   单架构包命名成 Universal，也不恢复 Windows/Linux target。
2. 五个 Swift 业务模块、Project Library v1、SQLite schema、task/diagnostic/scenario JSON、
   Resolve CSV 字节、OCR-first、Provider/recognition 与 Keychain machine-local 语义不变。
3. `.codex/refactor/**` 是不可改写的历史证据，即使包含 `.mjs`、截图或旧路径也必须保留；
   它不进入 App bundle、CI runtime 或 production dependency，不能因“删除 Node”而清空。
4. Paddle Python runner 是原生产品的受管 OCR helper，不属于 Node/Electron。最终保留 Python
   源与 `requirements-ocr.txt`，但迁到唯一 canonical App resource 位置；不捆绑可执行 Python、
   venv、model cache、用户数据或联网安装产物。
5. 自动测试与包/data audit 使用临时 Application Support / Project Library、fake credentials/
   network/process；不得读取、迁移、删除或覆盖用户默认 Library 与 Keychain。
6. release secrets 只存在于受保护 CI secret/keychain/notary profile 边界；日志、artifact、
   xcresult、manifest、命令行回显和 Git 历史不得含 certificate、private key、password、API key。
7. 修改代码/脚本时更新签名、资源、工具版本、清理陷阱和数据升级等非显然注释，并同步根目录
   `AGENT.md`。不改写历史 review 或用事后编辑伪造既有 Gate evidence。

## 签名与分发声明分层

本阶段必须明确区分本地/PR 可执行验证与真正的外部分发，禁止把 ad-hoc 签名描述为已通过
Gatekeeper 的公开发布包。

| Lane | 必须证据 | 允许的声明 |
| --- | --- | --- |
| Local / PR archive | Release Universal app、hardened runtime、最小 entitlements、ad-hoc `-`、`codesign --verify --deep --strict` | “可构建、可归档、ad-hoc 签名的本地验证包” |
| Developer ID distribution | Developer ID Application 签名、secure timestamp、hardened runtime、完整 nested-code 验证 | “已用 Developer ID 签名” |
| Notarized public release | Developer ID + `notarytool` Accepted + app/DMG staple/validate + Gatekeeper assessment | “已公证并可供外部分发” |

Local/PR lane 是每次 Gate 必做且不需要私钥。若 Owner 要求正式外部分发，Developer ID/notary
lane 也是 release Gate 必做；本地缺 credential 时按 `PHASE_GATES.md` 记 `BLOCKED_ENV`，可由
受保护 CI 对同一 commit 的等价证据替代，但不能降级为 ad-hoc 后仍声称 notarized。若本阶段
只获授权做 cutover/ad-hoc archive，review 必须明确“未发布、未验证 Gatekeeper 公证”，不得
创建 GitHub Release。

## 产物与版本契约

1. 默认保留当前 macOS 发布形式：同一个已验证 Universal `SlateSync.app` 生成 `.zip` 与 `.dmg`。
   如果 Owner 决定只保留一种格式，必须在 WP-0 记录兼容/发布决策，不能在实现中顺手删除。
2. Release 文件名包含产品版本且不声称单架构，例如 `SlateSync-<version>-macOS-universal.zip`
   与 `.dmg`。二者必须来自同一 app payload/hash lineage；生成 `SHA256SUMS` 与 JSON manifest。
3. tag `vMAJOR.MINOR.PATCH`、`CFBundleShortVersionString`/`MARKETING_VERSION` 和 artifact version
   必须精确一致。`CFBundleVersion`/`CURRENT_PROJECT_VERSION` 使用 WP-0 冻结的单调整数来源；
   无合法 tag 或版本不一致时 release fail-closed。
4. DMG/ZIP 构建命令、volume layout、压缩方式、locale/timezone 和输入清单应可重现；由于 DMG、
   code signature/notary timestamp 可能非逐字节确定，不要求跨运行 hash 相同，但必须保证内容、
   app hash lineage、架构、版本、签名与 resource manifest 可追溯。
5. `.xcarchive`、DerivedData、临时 keychain、export staging、DMG mount、notary submissions 与最终
   artifacts 默认写入忽略的 Gate/result 临时目录；除有意的 GitHub Release artifact 外不提交 Git。

2. **FIFO lease（CARRY-06）**：在 supervisor/service actor 内维护显式 waiter 队列和
   continuation，入队顺序即获取顺序；取消 waiter 只完成自己的 continuation，不关闭当前
   lease；`close()`/generation 变化要以明确错误唤醒排队者并等待活动 lease drain。不得以
   `Task.sleep` 轮询替代等待协议。
3. **Persistence/OCR 复验（CARRY-03/04/05）**：运行失败注入目录补偿、default project
   保护、OCR_CLOSED/取消区分的回归；若发现实现与台账描述不一致，先修代码和注释，再更新
   证据，不能仅改状态文字。
4. **并发与资源回归**：覆盖多 waiter、配置切换、取消竞态、worker 退出恢复、session clear、
   permanent close 和临时资源清理；记录 active/pending/worker/launch 计数，确保无 waiter
   泄漏、双 resume、误杀或 busy polling。
5. **交付物**：CARRY 代码/测试提交、`sm09-carry-closure.json`（每项结果、测试命令、
   commit/source hash、剩余风险）、更新后的台账状态和必要的 `AGENT.md` 方案说明。

## 完成定义与最终交接

SM-09 只有在 pre-cutover 全矩阵证据完整、legacy removal 有逐项替代、最终 tree/CI/Gate/release
不依赖 Node、Universal archive 和 ZIP/DMG 的架构/资源/签名/data audits 通过、独立 review 无
阻断项并获得 Owner 最终批准后才完成。如果 scope 声称公开分发，还必须有同 commit 的
Developer ID/notary/staple/Gatekeeper evidence；只有 ad-hoc 时必须明确限制声明。

主要风险包括：在最后一次差分前删除 oracle、把历史 manifest 改写成“从未存在”、最终 Gate
仍暗含 Node、双单架构包冒充 Universal、ad-hoc 冒充 notarized、release secret/临时 keychain
泄漏、DMG/ZIP 不是同一 app、Paddle helper 被误删或捆绑 venv，以及自动升级测试碰到真实用户
Library。所有风险都由两点证据链、严格 inventory/denylist、临时根、签名分层和 fail-closed
Gate 关闭。

SM-09 `COMPLETE` 表示当前迁移和首次 native release pipeline 已获批准；后续每个版本仍需按
同一 native Gate、版本、签名、公证、artifact 和数据 smoke 流程执行，不能复用旧 notarization
结果或把本阶段审批当作永久发布授权。
