# SM-05 — CSV, metadata and scenarios

## Objective

Port Resolve CSV decoding, normalization, merge and byte-preserving encoding;
Kinefinity metadata parsing and bounded material-directory scanning; and
Scenario Profile observation, fingerprinting, similarity and persistence
coordination to native Swift background services.

SM-05 is complete only when the native implementation is differentially
compatible with the reviewed Electron behavior, every byte golden passes, the
deterministic 10,000-row workload meets the timing gate, and no SM-06 media/OCR
or SM-07 provider/recognition work enters the phase.

## Admission and fixed boundaries

- SM-04 is `COMPLETE`; its v1 `project.sqlite` schema, `ScenarioStore`, project
  leases and transfer formats are the persistence foundation for this phase.
- Keep Resolve CSV encoding, BOM, delimiter, line ending, final-newline choice,
  header/row/column order, CSV quoting and untouched cell values compatible
  with the frozen JavaScript behavior. A round trip may canonicalize quoting in
  the same places as the reviewed baseline, but must match its exact bytes.
- Keep Scenario `schemaVersion = 1`, `fingerprintVersion = 1`, 32-character
  fingerprint, weighted similarity, six-decimal rounding, matching threshold
  `0.85` and ambiguity margin `0.05` unless project settings explicitly supply
  compatible values. Do not add a schema v2.
- Keep metadata scanning read-only, bounded by expected Resolve material keys,
  depth and file-size limits. Tests use only checked-in fixtures and temporary
  directories; the user's real media volumes, Application Support and Project
  Library are out of scope.
- Run CPU/file work outside the main actor. Services must be `Sendable`, honor
  Swift cancellation at bounded checkpoints and publish no partially built
  table, scan result, profile or observation after cancellation/failure.
- SM-05 may add service methods to the SM-04 Scenario persistence owner, but it
  must not change SQLite filenames, tables, indexes, pragmas, JSON keys, project
  isolation or transfer format.
- Do not port PDF/image preparation, Vision/PaddleOCR, provider discovery,
  recognition orchestration, SwiftUI workspace integration, Electron removal,
  packaging, signing or notarization. Those remain SM-06 through SM-09.
- Electron modules remain compatibility oracles and differential-test inputs;
  they are not deleted or bypassed in this phase.

## Work breakdown

### WP-0 — Freeze the behavioral inventory and fixture contract

1. Inventory every exported CSV, material-key, metadata-source, structure and
   Scenario function plus every Node regression named in the sources above.
2. Create `Tests/SlateSyncWorkflowTests/Fixtures/SM05/` with CSV, metadata,
   scanner-tree, scenario-observation and performance manifests. Copy binary
   CSV fixtures without transcoding; record byte length and SHA-256.
3. Add a contract audit that maps every legacy test behavior to a native test
   ID. The audit fails for a missing mapping, changed golden hash, untracked
   fixture, accidental `.DS_Store`, real-user absolute path or scope-owned file
   from SM-06 and later.
4. Capture the initial Swift-versus-JavaScript differential output before
   replacing behavior. Any intentional discrepancy must be documented in this
   package and approved before implementation; otherwise it is a defect.

Deliverable: a stable fixture manifest and a machine-checkable coverage map,
not a generated golden derived from the Swift code under test.

### WP-1 — Close domain and service contracts

1. Reuse `ResolveCSVTable`, `ResolveCSVFormat`, `ScannedSlateMetadata`,
   `ScanStats`, `ScanResult`, `ScenarioProfile` and existing project settings.
2. Add only the missing typed inputs/outputs needed for merge options, sparse
   edits, metadata structure templates, Scenario observations and match
   outcomes. Preserve current Codable wire keys and optional/null semantics.
3. Expand `CSVProcessing` into small capability protocols or a compatible
   façade for decode, merge, standalone export and encode. Define scanner and
   Scenario processing protocols so tests can inject temporary roots and the
   later recognition phase can compose them without UI dependencies.
4. Validate field-format templates, comment markers, scan bounds, normalized
   rectangles and Scenario matching numbers at the domain boundary. Stable
   `SlateSyncError` codes must distinguish invalid CSV, invalid options,
   unsupported metadata, unsafe scan input, cancellation and invalid profile.

Deliverable: compiling Sendable contracts with Codable round-trip tests and no
untyped `[String: Any]` business boundary.

### WP-2 — Complete the byte-compatible CSV codec

1. Harden `ResolveCSVEngine.decode` for UTF-8 with/without BOM, UTF-16LE/BE
   with BOM, comma/semicolon detection, CRLF/LF/CR, quoted delimiters, escaped
   quotes, embedded newlines, trailing empty cells and final-newline choice.
2. Reject an empty/missing header, unsupported encoding, an unclosed quoted
   field and invalid delimiter/line-ending configuration with stable errors.
3. Make encoding preserve record order and format while matching the legacy
   minimal-quoting and double-quote rules. Do not normalize unrelated cells,
   Unicode text or whitespace.
4. Run exact byte length and SHA-256 assertions for every reviewed source and
   round-trip output. Include a one-byte mutation test proving the golden gate
   fails independently of semantic table equality.

Deliverable: codec goldens pass before merge behavior is introduced.

### WP-3 — Port normalization and material identity primitives

1. Port full-width digit and Chinese-number conversion, field-width handling,
   uppercase Scene suffixes and non-truncation of values wider than a template.
2. Port canonical material-key extraction/parsing for Reel Name, File Name and
   Clip Name, including camera/card/clip zero padding and the `C0XX` video-code
   rule. Conflicting identifiers must remain unmatched rather than guessing.
3. Port Resolve header alias lookup for English/Chinese headers regardless of
   order, canonical appended-header names and material-key collection.
4. Port take-sequence anomaly detection, including duplicate takes and takes
   that fail to restart after a clip gap. Preserve deterministic output order.
5. Port comment canonicalization for good/hold/reject states and project-level
   custom comment markers. Strict export may canonicalize all comment cells;
   merge must not rewrite unmatched rows beyond reviewed behavior.

Deliverable: pure-function tests pass independently of filesystem, SQLite and
UI code.

### WP-4 — Port Resolve merge, sparse edits and standalone export

1. Build one indexed merge pipeline; never scan all records for every Resolve
   row. Consistent duplicate slate records merge once, conflicting duplicates
   write nothing, and one slate record updates every matching Resolve row.
2. Preserve all original rows and columns. Append missing target columns in
   canonical order, retain unmatched rows, backfill multi-scene values and
   apply custom Scene/Shot/Take formats only to owned target fields.
3. Reconcile Kinefinity `Sensor FPS` and `Shot Date` into `Camera FPS` and
   `Shoot Day`: fill empty targets, preserve existing targets on missing or
   conflicting metadata, and allow one valid metadata field even when another
   field or slate record is incomplete.
4. Apply sparse edits only for validated `row:column` keys within bounds and
   after the base merge. Invalid keys are ignored during compatible snapshot
   restore and rejected at explicit mutation APIs; edits never reorder rows or
   columns.
5. Build standalone Resolve output when no source CSV is present. Skip invalid
   or incomplete records, use the reviewed default UTF-16LE+BOM/comma/CRLF
   format and honor custom formats/comments.
6. Return table, bytes and audit information (`missingMetadataKeys`, unmatched
   material keys and sequence anomalies) as immutable values. Cancellation or
   one failed validation publishes none of them.

Deliverable: the reviewed merged and standalone byte hashes match exactly.

### WP-5 — Port metadata parsing, structure learning and scanner

1. Implement a metadata-source registry with Kinefinity `slate.txt` as the
   first v1 source. Match source names case-insensitively and reject unsupported
   files instead of attempting generic parsing.
2. Parse `Clip Name`, `Sensor FPS` and `Shot Date` into the existing canonical
   metadata DTO. Normalize FPS and `YY-MM-DD` exactly as JavaScript does and
   derive the material key from the clip name without retaining raw file bytes.
3. Port default `dirname + "-slate.txt"` probing, fixed-name templates,
   per-camera learned structures and bounded fallback enumeration.
4. Implement the read-only scanner with defaults `maxDepth = 4` and
   `maxFileBytes = 2 MiB`, accepted bounds `1...12` and
   `1...100 MiB`, expected-key pruning, directory-depth accounting and file-size
   rejection. Empty expected keys fail before traversal.
5. Preserve the six `ScanStats` counters, contextual warnings and complete
   `missingKeys` reconciliation, including material directories that never
   existed. Normalize result ordering deterministically for differential tests.
6. Check cancellation between directory batches and file reads. Symlinks and
   non-regular files are not followed; unreadable entries become warnings only
   where the legacy scanner would continue safely.

Deliverable: parser and temporary-directory scanner fixtures match the
reviewed metadata, warnings, counters and missing-key results.

### WP-6 — Port Scenario observation, fingerprint, similarity and matching

1. Define a typed observation input independent of SM-06 OCR implementation:
   pages, views, dimensions, confidence, normalized bounding boxes and source
   metadata. SM-06 will adapt Vision/Paddle output to this contract.
2. Port OCR page normalization, header-token/camera-group discovery,
   quantized row/column bands, page/view shapes, canonical field aliases,
   inferred union regions and required/inherited field flags.
3. Reproduce stable JSON key ordering, number normalization and SHA-256
   fingerprint generation exactly; fingerprints remain version 1 and the first
   32 lowercase hexadecimal characters.
4. Port profile normalization/public projection/prompt instruction. Cap labels,
   prompt hints and list sizes at the reviewed limits; reject malformed
   rectangles and future schema versions without silently manufacturing data.
5. Port similarity weights: pages `0.20`, headers `0.40`, camera groups `0.15`,
   columns `0.15`, rows `0.10`; exact fingerprints score `1`; all scores use
   six-decimal rounding.
6. Implement matching with the project threshold and ambiguity margin. Score
   all profiles deterministically, reuse only a confident best match, create a
   new profile otherwise, and report `created`/`reused`, score and ambiguity.
7. Extend the SM-04 `ScenarioStore` with one atomic apply operation using the
   existing v1 schema: create/reuse, sample-count/last-used update and
   observation insert either commit together or roll back together. Concurrent
   identical observations resolve to one canonical profile and two committed
   observations without lost sample counts.

Deliverable: exact fingerprint/profile fixtures, threshold-edge/ambiguity
tests and close/reopen SQLite tests pass without schema drift.

### WP-7 — Compose background services and cancellation behavior

1. Add a `SlateSyncWorkflow` composition façade that owns the CSV engine,
   metadata scanner and Scenario processor without introducing SwiftUI or
   provider dependencies.
2. Ensure actors do not hold mutable table/profile state across unrelated
   projects. Inputs and outputs are value snapshots; Scenario persistence is
   always acquired through the existing project runtime/lease boundary.
3. Add cancellation regressions at CSV parsing/merge, directory traversal and
   Scenario scoring checkpoints. Verify retry after cancellation starts from a
   clean state.
4. Add structured, secret-free diagnostics containing counts and durations,
   never CSV cell contents, OCR text, absolute media paths or profile prompt
   hints.
5. Update comments on every added or materially changed code path to explain
   compatibility, ordering, cancellation or transaction invariants.

Deliverable: service-level tests demonstrate no main-actor work, cross-project
state leak, partial publication or post-cancellation persistence.

### Deterministic 10,000-row timing sample

`PERF-01` is generated from a fixed seed and manifest rather than checked in as
a large mutable CSV. It contains exactly 10,000 Resolve rows, 12 columns, four
cameras, zero-padded and wide clip numbers, 80% matched rows, 10% unmatched
rows, 5% repeated Resolve rows and 5% deliberately conflicting/invalid
identities. Every 97th Notes cell contains a delimiter, quote or embedded
newline. Metadata includes compatible, missing and conflicting FPS/date cases;
sparse edits touch 1% of valid cells. The output row count, column order, byte
length and SHA-256 are fixed in the reviewed manifest.

The benchmark measures native `decode → material index → merge → sparse edits
→ encode` in a Release build with one warm-up and five measured runs. Admission
requires all semantic/hash assertions plus:

- median 10,000-row end-to-end time no greater than 2.0 seconds on the recorded
  review Mac;
- no measured run greater than 5.0 seconds; and
- median 10,000-row time no greater than 2.5 times the corresponding 5,000-row
  prefix median, guarding against accidental quadratic behavior.

The review report records hardware, OS, toolchain, build configuration, all
five samples and both medians. Thresholds and fixture seed may not be changed
after seeing an implementation result without explicit Owner review. A timing
failure is `FAIL`; an actually unavailable Release toolchain is `BLOCKED_ENV`.

## Review reconciliation and deferred compatibility edges

The post-construction GLM review and the native review were checked against the
retained JavaScript modules rather than accepted from assertions alone. The
following discrepancies are closed in the working tree before a review commit:

- sequence anomaly, metadata-conflict, sidecar, record-group and two-pass
  normalization iteration now follows JavaScript first-occurrence order;
  sparse edits use an ordered typed list instead of a randomized Dictionary;
- card/video material tokens intentionally do not apply NFKC, so full-width
  identifiers remain invalid just as they are in `resolve-csv.js`;
- `scenario_observations.observation_json` keeps the v1 flattened Profile keys
  at its root, and Scenario writes now pass through the project-addressed
  `ProjectRuntime` lease boundary;
- score ties preserve `last_used_at DESC` input order, public similarity
  normalizes both inputs, imported orientation/page numbers and UTF-16 text
  limits match `profile.mjs`, CSV line splitting excludes U+2028/U+2029, and
  Resolve/standalone export rejects empty effective output;
- reviewed metadata, scanner-tree, Scenario and performance fixtures have
  unique SwiftPM resource names and frozen SHA-256 entries. Missing resources
  fail tests instead of becoming skipped coverage.

Three low-reach boundaries remain explicit later-phase handoffs rather than
silent claims of exact compatibility:

- the native scanner rejects a missing or non-directory root with
  `METADATA_DIRECTORY`; Electron returns an all-missing result with a warning.
  The native fail-closed behavior is retained as a filesystem safety boundary;
- `ResolveSlateRecord` accepts typed `TakeStatus`; parsing legacy strings such
  as `_OK`, `_KP`, `过`, `保`, `ng`, `x` and `×` belongs in the SM-06/SM-07
  OCR/CSV adapter before it calls the SM-05 merger;
- malformed canonical material keys can only reach diagnostic helpers, where
  Swift scalar ordering may differ from JavaScript `localeCompare`. Valid
  canonical keys use the numeric comparator and remain deterministic.

These notes do not approve SM-05 or advance lifecycle state. Any decision to
require exact missing-root behavior, move take-status parsing into SM-05 or
support malformed-key ordering must be made before the consuming phase relies
on that edge.

## Risks, rollback and later-phase handoff

- **Byte drift:** Swift `String`/Unicode and newline handling can alter bytes.
  Mitigation: Data-first encoding detection, independent hashes and a mutation
  control. Roll back the codec commit rather than update goldens to fit output.
- **Quadratic merge:** repeated row/record scans can pass small unit tests.
  Mitigation: indexed material keys plus the 5k/10k scaling gate.
- **Filesystem nondeterminism:** enumeration order, unreadable files and links
  can make scans flaky or unsafe. Mitigation: bounded regular-file traversal,
  deterministic normalization and temporary trees.
- **Fingerprint drift:** floating-point formatting or unordered collections can
  fork existing profiles. Mitigation: stable serialization and exact fixture
  fingerprints before persistence integration.
- **Scenario race/partial commit:** scoring and persistence split across actors
  can lose counts or observations. Mitigation: deterministic scorer plus one
  existing-schema SQLite apply transaction and concurrency regressions.
- **Phase leakage:** wiring real OCR, recognition providers or UI would make the
  Gate review ambiguous. Mitigation: the contract audit rejects SM-06+ owned
  implementations; adapters are left as explicit handoff notes.

If a frozen compatibility invariant cannot be met without schema/format churn,
stop SM-05 and record a blocking decision in `DECISION_QUEUE.md`. Do not change
the baseline, advance `CURRENT_STATE.json`, touch `.codex/refactor` historical
evidence or compensate with an undocumented compatibility exception.
