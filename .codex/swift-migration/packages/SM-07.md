### 识别与网络参数

| 项目 | 固定要求 |
| --- | --- |
| 输入 | 1～20 页；每页 1～3 个 JPEG/PNG/WebP Data URL 等价图像值；SM-07 原生边界实际使用 SM-06 `PreparedImage` bytes |
| 视图 | standard 每页只发 full；high 发 full＋core-detail；高精度 audit/review 只发 core views，若无 detail 则回用 full |
| 请求预算 | 默认 80 MiB 兼容 envelope，目标为 `floor(maxRequestBytes × 0.94)`；中文/emoji、CSV、scenario ID、custom prompt 和 Base64 均按 UTF-8 序列化字节计入 |
| Provider 输出上限 | Responses `max_output_tokens=16000`；Chat Completions `max_tokens=16000`；均非流式，Responses `store=false` |
| 模型 timeout | 单次默认 180,000 ms；显式正数四舍五入并 clamp 到 30,000～3,600,000 ms |
| timeout retry | 默认 1 次；显式整数 0～3；只有 headers/body deadline timeout 重试，普通连接失败、HTTP/API 错误、解析失败不重试 |
| retry deadline | 每次 attempt 获得完整单次 timeout；同一 attempt 的 headers 与 body 共用 deadline；外部取消不重试 |
| 逐页并发 | 默认 2；`MODEL_PAGE_CONCURRENCY` 仅接受 1～6 整数，非法值回到 2；输出始终按输入页序 |
| 全局并发 | 默认 1；`MAX_CONCURRENT_RECOGNITIONS` 仅接受 1～16；达到上限立即 429，不排队；动态降低只约束新任务，已运行任务继续排空 |
| progress | percent clamp 0～100、取整且单调；observer throw/disconnect 不得中断识别；阶段为 starting、ocr、primary、audit、review、page-complete、merge、complete/canceled |
| 错误 | 页失败包装 `第 n/N 页识别失败`；取消统一 `RECOGNITION_CANCELED`；provider/client 分类、HTTP status 与 retryable 含义稳定 |

### 结构化输出 fallback 与 prompt 顺序

1. OpenAI Responses 默认 `text.format=json_schema`。自定义 Responses 可选择
   `json_schema`、`json_object` 或 prompt-only；非 schema 模式必须把完整 schema 附在
   system prompt，不能只发送“返回 JSON”。
2. Chat Completions 的首选模式来自 Provider/model：OpenRouter 明确不支持 structured
   outputs 的模型从 `json_object` 开始，其余从 `json_schema` 开始；自定义 Provider
   使用持久化模式。
3. 只有 400/404/422 且错误语义明确指向 response_format/json schema/json object/
   structured output 不支持，或 OpenRouter 报 no compatible endpoint，才按
   `json_schema → json_object → prompt` 逐级降级。认证、额度、限流、5xx、网络和
   取消不得触发格式降级。
4. prompt 拼接顺序固定为：阶段 system prompt → 非空 custom project context → 非空
   slate CSV 高可信度上下文 → field width instruction → Resolve Comments instruction →
   Scenario Profile instruction。primary、audit、review 全部携带相同项目上下文；review
   另加只允许目标 material keys 的 user instruction。
5. full schema、core schema、三个 system prompt 和合成探针 schema 逐字冻结。请求可做
   JSON 结构等价比较；prompt、状态文本、warning 与 evidence 必须做 UTF-8 exact golden。

### WP-3 — URLSession transport、deadline、retry 与协议失败

1. 实现 actor-owned `URLSessionProviderTransport`。生产使用 ephemeral URLSession 与
   显式 request；测试注入专用 URLProtocol/session configuration。不得使用同步网络、
   shell、WebView、第三方 HTTP client 或全局共享 session state。
2. 分别构建 GET discovery 与 POST JSON。POST 固定 `Content-Type: application/json`；
   discovery 固定 `Accept: application/json`；Bearer、OpenRouter headers 只在 registry
   决定后附加。URL path 通过结构化 URL 组合，不能字符串拼接出 query/credential。
3. 每个 attempt 建立单一 deadline，覆盖等待 response 与读取 body；timeout 必须 cancel
   对应 URLSessionTask、等待 completion/cleanup 后再重试。父 operation 取消优先于
   timeout，且永不 retry/fallback。
4. timeout 只按固定 0～3 次规则重试；connection、TLS、DNS、HTTP/API error、invalid
   JSON/body 和结构化模型输出错误一次失败。请求格式 fallback 与 timeout retry 是两层
   独立状态机，测试断言精确调用次数和 mode 顺序。
5. HTTP 非 2xx 或 JSON `error` 使用 provider message/status；choice-level error 同样
   失败。错误中即便回显 key/Authorization 也必须先脱敏。空/畸形/超限 response 按
   WP-0 策略确定失败，不能截断后当成功。
6. `close()` 取消并排空所有 owned tasks/delegate callbacks；重复/并发 close 安全。
   已关闭 transport 不接受新请求，旧 generation completion 不得回到新 session。

交付：Responses/Chat/GET transports 与所有失败模式在 deterministic URLProtocol 下通过。

### WP-4 — 模型发现、静态 fallback 与能力探针

1. `ModelDiscoveryService` actor 实现 15 秒 discovery、5 分钟 cache、force refresh、
   status/body 方言、内建 fixed overlay、modality 过滤、known vision family inference、
   vendor/price/rating 解析、stable sort 和 physical ID 去重。
2. OpenAI discovery 交集保留 key 实际可见且 catalog 判定为视觉的模型；OpenRouter
   信任完整 modality/parameter metadata 并排除 text-only、image-output、embedding、
   audio/generation；Token Plan/DashScope 保留各自 licensed fixed set。
3. custom `/models` 缺失时保留 manual pending。完整 metadata 的 image-in/text-out 可
   declared；维护模型族可 inferred；信息不全/未知必须 pending；显式 failed/canceled
   始终覆盖 metadata。
4. `ModelCapabilityProbeService` 发送冻结的 synthetic image/schema，不读取项目。
   batch 最多两个并行；进度 clamp、单调、observer failure-safe；同一 Provider 同时
   只有一批探针，否则 409。
5. 取消/删除/编辑 Provider 要 cancel 探针并等待 owned tasks 排空。已完成结果可保存，
   canceled 保持不可选；只有 current revision 且全局配置原子写成功，才替换 live cache。
   保存失败保持原 registry，不部分追加 manual IDs。
6. legacy JSON Schema text probe 与 UUID vision probe 分开，不允许纯文本 echo 通过视觉
   能力。所有请求/响应/进度/持久化字段使用 whitelist，拒绝 injected fake 伪造 verified。

交付：发现/探针分类、缓存时钟、revision/save/delete/cancel 竞态和无 secret 公共结果通过。

### WP-5 — Prompt、schema、Provider payload 与响应解析

1. 将 `SLATE_SCHEMA`、`CORE_SLATE_SCHEMA`、`SYSTEM_PROMPT`、
   `CORE_AUDIT_SYSTEM_PROMPT`、`CORE_REVIEW_SYSTEM_PROMPT` 逐字迁移，并用 manifest
   hash/golden 防漂移。core schema 只含 card/video/scene/shot/take/status/confidence。
2. prompt composer 保留 custom prompt trim、slate CSV 行顺序/标签/最终权威说明、field
   width（1～6 个 X）、Comments token、Scenario headers/camera groups/region/hints 的固定
   顺序。项目设置始终高于 Profile output metadata。
3. 为 Responses 和 Chat 分别实现 typed payload builder：content item 名称、schema
   包装层、image detail、filename/page wording、multi-view/core wording、OpenRouter
   provider 字段必须结构等价。请求 builder 不读取 credential 或执行网络。
4. structured-mode fallback 按固定状态机重建完整 payload；不得复用已消费 body，
   不得在 prompt-only 遗漏 schema，也不能把 Provider 400 一律当 capability fallback。
5. response extractor 接受 Responses `output_text` 或 output/content `output_text` parts，
   Chat string 或 text parts；无文本明确失败。只剥离包裹整个结果的可选 JSON code fence。
6. 请求 envelope 的 0.94 预算在 OCR/Provider 前通过 SM-06 不可变压缩能力执行；每档
   用真实 `JSONEncoder` UTF-8 bytes 测量完整兼容输入，仍超限则零网络调用。

交付：三个阶段的 prompt exact goldens、两 transport payload fixtures、fallback 调用序列和
预算边界通过。

### WP-6 — 结果规范化、页合并与连续性修复

1. Provider JSON 使用受控 JSON value 解析，再做兼容规范化；不能让严格 Codable 因旧
   响应缺少可空字段/包含额外字段而拒绝。顶层非对象或无 `records` 数组仍明确失败。
2. 保留 NFKC、中文数字转阿拉伯数字、scene 多值 ` / `、后缀大写、1～6 位补零、
   card `A10→A010`、video `15/C 15→C015`、C115/C0115 拒绝、sourcePage 1～20、
   confidence 非法回 low、warning 只留字符串的行为。
3. 每页记录最终 ID 为 `record-page-{page}-{index}`，sourcePage 来自实际页而非模型；
   页结果按输入顺序合并，即使网络完成乱序。页内记录顺序保留模型输出。
4. 按 reel＋clip 顺序向下继承 scene/shot，但不覆盖 `reviewRequiredFields`；保留跨页
   继承、同 scene 限制、warning 文案和人工复核标记。
5. 移植 sandwiched row 与 dropped shot tens 两类确定性修复、material sort、共享
   sequence anomaly warning，以及 standard 模式建议 high 的附加 warning。不得扩展为
   新的“智能纠错”。
6. aggregate usage 只累加有限数值和既有 token key；internal cost 可供诊断计算但不进入
   `RecognitionData`/public DTO。格式化在全部合并/修复后按项目 field widths 执行。

交付：baseline normalization、跨页/乱序、30 omission/4 conflict、数字移位和异常 warning
差分全部通过。

### WP-7 — 逐页执行与 high-accuracy 三阶段复核

1. `RecognitionPagePipeline` 使用 bounded task group，默认 2、有效范围 1～6；外部取消
   必须取消并排空全部 child tasks。普通页失败对 siblings 的策略按 WP-0 冻结/批准结果
   执行，但 coordinator 必须持有并排空它们。并发完成不改变最终页序或 completed count
   的单调含义。
2. standard 每页只执行 primary。high 每页让 primary(full＋details) 与 independent
   audit(core-only) 同时开始；两者完成后按 material key 合并。
3. primary 重复/缺 key、audit 缺 key、audit-only、缺字段补全和冲突分别保留现有
   warning/降 confidence 行为。只有存在 conflict 或 audit-only 才执行第三次 target
   review；目标列表、字段和值格式 exact。
4. review 未确认 audit-only 时移除候选；确认时更新核心字段并降 confidence；冲突字段
   最终仍无法确认时置 nil、加入 `reviewRequiredFields`，绝不保留猜测值。
5. 每 stage 关联 page/stage/request summary/response/normalized result/OCR evidence 给
   diagnostic capture；不复制图片 Data URL。页错误保留 provider/client 分类；取消
   不包装成普通页失败。

交付：standard/high 调用数、同页并行、跨页上限、merge/review 语义和失败排空通过。

### WP-8 — OCR-first 总编排、并发、进度、取消与持久化

1. 用完整 `RecognitionCoordinator` façade 接管 start/progress/cancel/close。为保留 limiter
   的 fail-fast 优先级，执行顺序固定：acquire global slot/register operation → validate
   project/input → prepare/request-fit → local OCR → Scenario selected/auto/fallback → compose
   prompts → page pipeline → merge/format → diagnostic/task/project activity persistence →
   public result。
2. required OCR 失败/空 blocks、SM-06 取消或 direct-PDF rejection 均零 Provider 调用；
   optional OCR degradation 继续 image-only 并把同一稳定 warning 写入 progress、result、
   task summary 和 diagnostic。
3. 显式 Scenario ID 不存在是 400；无显式 ID 且有 OCR 时通过现有
   `ScenarioMatchingService`/`ProjectRuntime` 选择并保存；无 evidence 或学习失败按旧语义
   fallback。项目 fieldFormats/comments 永远高于 Profile output。
4. global limiter 默认 1、范围 1～16、fail-fast 429、release 幂等。每个运行有 operation
   ID/generation；按 project cancel 取消该项目所有 active operations，并等待 media、
   URLSession、Scenario/persistence tail 和 limiter/lease 真正排空后才返回 canceled=true。
5. progress stream 支持多个观察者且独立取消订阅；百分比单调、断开的 observer 不影响
   任务。取消/替换/close 后不得有迟到 progress、retry、format fallback、cache write、
   Scenario write、task completion 或 success delivery。
6. 识别完成现有 draft 时 update 同一 task；无 draft 时创建 task。保存 project settings
   snapshot、last recognition defaults、Scenario 元数据、OCR summary、usage、duration、
   records/editedRecords 与 diagnostic ID，保持 task v1 keys。取消门检查覆盖 Provider 返回、
   diagnostic save、task save 和 activity touch 之间的每个 await。
7. diagnostic 成功/失败内容按旧契约保存到当前项目，但图片只记尺寸/数量，不记 bytes；
   credential、Authorization、Base URL query、绝对路径和 OS environment 永不持久化。
   OSLog 只记 provider/model、阶段、页/记录计数、耗时和脱敏错误，不记 prompt、OCR 全文、
   CSV 行、模型原文或用户文件名。
8. close 为 terminal、single-flight、可重复；先拒绝新任务，再 cancel/drain 所有识别和
   探针，最后关闭 media/transport。项目关闭/删除与识别相撞时通过 ProjectRuntime lease
   失败或等待，不缓存 raw store/context 越过租约。

交付：服务级 OCR-first、global/project 并发、cancel truthfulness、持久化 await-boundary、
关闭/重开和 SM-08 façade 回归通过。

## 完成定义、风险与后续交接

SM-07 完成必须同时满足：所有内建/legacy/UUID Provider 路由正确；发现/探针 revision 与
secret 安全；Responses/Chat/fallback/timeout/retry 在 URLSession deterministic fakes 下全覆盖；
prompt/schema/normalization/high-accuracy 差分通过；OCR-first、Scenario、并发、progress、
cancel、diagnostic/task persistence 生命周期完整；旧阶段回归、clean Gate 与 Owner 批准齐全。

- **URLSession 语义差异：** redirect、代理、TLS/URLError、body delivery 与 undici 不同。
  通过 WP-0 oracle 和 URLProtocol fixture 固定可观察行为；安全收紧单独决策。
- **Prompt 漂移：** 长中文 prompt 容易在重排时无意改字。用 UTF-8 hash 加 exact golden，
  任何产品文案改动不得混进本迁移阶段。
- **结构化响应容错：** request schema 是 strict，不代表历史 response decoder 应 strict。
  先解析 JSON value 再兼容规范化，避免额外/缺省字段破坏旧模型结果。
- **重试乘法：** page concurrency、high stages、format fallback 与 timeout retry 叠加会放大
  调用数。状态机测试必须断言每条路径的上界，取消立即停止继续尝试。
- **actor 重入：** registry save、Scenario/persistence 和 close 均跨 actor await。使用
  operation/revision generation，在 await 后重新验证，不让旧 completion 写入新状态。
- **诊断与隐私：** 项目内诊断需要足够复核信息，但 secret、图片 bytes、绝对路径和环境
  永不进入持久化；OSLog 进一步只保留计数和分类。
- **阶段越界：** SM-08 获得 Provider summaries、discovery/probe API、recognize façade、
  progress/cancel 和 typed result；它只负责 SwiftUI/AppKit 工作流，不再实现第二套网络、
  prompt、normalization、limiter 或 persistence tail。SM-09 才删除 Electron。

规划完成不等于阶段完成。只有实施、专用审查提交、精确 SHA clean Gate、review report
和 Repository Owner 明确批准全部完成后，才能把 SM-07 标记为 `COMPLETE` 并开始 SM-08。
